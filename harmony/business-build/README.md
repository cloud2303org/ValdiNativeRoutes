# Portable ClientSQL business prerequisite

This directory builds the real `ClientSQLNativeModuleFactory.cpp` from Valdi
commit `15feb6530ceecb971f4c8519ea8ab77474b959db`, compiler-generated
`valdi_modules/client_sql/client_sql.{hpp,cpp}`, and the pin's portable SQLite
amalgamation. It exports the PIC static target `valdi_clientsql_ohos`.

Run `node scripts/harmony/prepare-business.mjs` after runtime preparation.
Inputs are staged under `.tools/harmony/business-inputs`; their provenance and
SHA-256 digests are recorded there. No Apple binary is used for OHOS.

Parent integration (the parent owns the runtime and application targets):

```cmake
add_subdirectory(path/to/harmony/runtime-build runtime)
add_subdirectory(path/to/harmony/business-build business)
target_link_libraries(your_host PRIVATE valdi_clientsql_ohos)
```

The business wrapper consumes the existing `valdi_runtime_ohos` target and its
public real-header include paths, definitions, and link dependencies. It does
not add a second runtime. Include `ClientSQLNativeModuleFactory.hpp` and register
the concrete factory before manager initialization:

```cpp
#include "ClientSQLNativeModuleFactory.hpp"
#include "valdi_core/cpp/JavaScript/ModuleFactoryRegistry.hpp"

auto registry = Valdi::ModuleFactoryRegistry::sharedInstance();
registry->registerModuleFactory(
    std::make_shared<Valdi::ClientSQLNativeModuleFactory>());
// RuntimeManager::postInit() consumes this shared registry; call it afterwards.
// Supply the owned disk cache to the RuntimeManager constructor.
```

The default factory resolves `Runtime::currentRuntime()->getDiskCache()` and
`getWorkerQueue()` when opening a database. Alternatively register a factory
constructed with the runtime-owned `Ref<IDiskCache>` and worker queue explicitly.
The parent must set an app-owned, writable, nonempty **absolute** disk root
(for example a `DiskCacheImpl` rooted in the application's persistent files
directory) before JS opens ClientSQL. The implementation creates
`<disk-root>/ClientSQLNative/<canonical-database-name>` and needs adjacent SQLite
WAL/SHM files and working POSIX file locks. An empty disk root fails rather than
falling back to an in-memory database. Persist this directory across app startup.

The generated module ID is `client_sql/src/ClientSQLNative`. Register into the
shared registry **before `RuntimeManager::postInit()`**: that method snapshots the
registry into the manager. Supply the disk cache to the `RuntimeManager`
constructor; `createRuntime()` passes it to each runtime. If a manager is already
initialized, use a separate `ModuleFactoryRegistry` containing the factory and
call `manager->registerModuleFactoriesProvider(registry)` once before business JS
starts. Re-registering the entire shared registry can duplicate unrelated
factories.

Registration must happen once for the manager/provider lifetime; linking the
static library alone does not register the factory. The explicit constructor
reference also retains its object file in normal static linking. Runtime startup,
asset delivery, registration, and device execution remain parent integration work.

## Preparation and provenance

`prepare-business.mjs` reads and verifies these source inputs against the exact
git object in `--git-source` (default `VALDI_FORK_SOURCE` or
`../Valdi-node-only`), not the checkout's HEAD:

- `src/valdi_modules/src/valdi/client_sql/BUILD.bazel`, `module.yaml`,
  `src/ClientSQLNative.d.ts`, and all three `native/ClientSQLNativeModuleFactory*`
  implementation/header/test inputs.
- `MODULE.bazel`, `bzl/valdi/BUILD.bazel`, and
  `third-party/sqlite/sqlite.BUILD`.

The BUILD closure is `client_sql_native_impl` → `client_sql_cpp`,
`//bzl/valdi:clientsql_runtime_sqlite`, and `//valdi:valdi_runtime`.
OHOS follows Bazel's default bundled-SQLite branch and compiles
`VALDI_CLIENTSQL_USE_BUNDLED_SQLITE`. SQLite uses exactly the pinned
`SQLITE_DEFAULT_MEMSTATUS=0`, `SQLITE_OMIT_LOAD_EXTENSION`, and
`SQLITE_THREADSAFE=1` definitions.

Bindings are freshly generated by `generate-bindings.ts` using the existing
Node `dumpAllSymbols` → annotation → model/module → combined C++ generator.
The program checks the real `.d.ts` with installed TypeScript 5.3.3. The generated
files match both available Bazel compiler outputs byte for byte. No compiler,
pipeline, or runtime source is patched. The output paths are:

```text
.tools/harmony/business-inputs/native/ClientSQLNativeModuleFactory.cpp
.tools/harmony/business-inputs/native/ClientSQLNativeModuleFactory.hpp
.tools/harmony/business-inputs/native/ClientSQLNativeModuleFactory_tests.cpp
.tools/harmony/business-inputs/generated/valdi_modules/client_sql/client_sql.hpp
.tools/harmony/business-inputs/generated/valdi_modules/client_sql/client_sql.cpp
.tools/harmony/business-inputs/sqlite/sqlite3.c
.tools/harmony/business-inputs/sqlite/sqlite3.h
.tools/harmony/business-inputs/sqlite/sqlite3ext.h
.tools/harmony/business-inputs/provenance.json
```

SQLite comes from the pin's `sqlite-autoconf-3530400.tar.gz` (3.53.4).
The archive SHA-256 is
`0e9483900e92cd5de8fd48d16bf9200145a61f7fd5be542a5ac81d8a9516eb9c`.
Preparation authenticates the archive before extracting the three named source
files; when Bazel's extracted sources exist it also compares their bytes.
The verified Bazel repository cache supplied the archive in this run.

Options: `--source`, `--git-source`, `--external`, `--bazel-out`, `--output`,
`--sqlite-archive`, and `--repository-cache`. Runtime source preparation must
already have populated `--source`. No Bazel build is run. If no matching archive
exists in the supplied/default caches, the script downloads only the immutable
official SQLite URL recorded in the verified MODULE, checks its SHA-256, and
caches it under the output directory. `--repository-cache` takes Bazel's `repos/v1`
directory (the parent of `content_addressable`).

`provenance.json` records native/build input hashes, every generator input hash,
Node/TypeScript versions, generated file hashes and matching Bazel output paths,
SQLite's official URL/archive hash/source ID, and each SQLite source hash.
Unchanged files keep their timestamps. Generated/staged outputs are ignored
build products; rerun preparation to recreate them.

## Reproduce validation without an application build

```sh
node scripts/harmony/prepare-business.mjs
source /Users/cloud/.config/harmony/env.zsh
node harmony/business-build/tests/verify.mjs --ndk "$OHOS_NDK_HOME"
```

The verifier defaults to `.artifacts/` under this directory. It builds both OHOS
ABIs with the installed NDK CMake/Ninja and imports each already-built runtime
archive from `.tools/harmony/runtime-<ABI>/`. The focused test driver recovers
real compile definitions/header paths from `Runtime.cpp`'s compile command and
the actual static dependency closure from that build's strict Ninja link.
It recompiles ClientSQL, generated bindings, and SQLite for each ABI, then links
all ClientSQL objects with `--whole-archive --no-undefined --no-gc-sections`.
The resulting shared proof libraries include the runtime/dependency code
statically; their only dynamic dependencies are `libc++_shared.so` and `libc.so`.
There are no TEXTRELs. The exported registration probe and real generated/SQLite
symbols are checked after linking. These proof libraries are not application
deployment artifacts.

`--runtime-root DIR` changes the parent of `runtime-x86_64` and
`runtime-arm64-v8a`; `--output DIR` changes the proof output directory;
`--host-cmake FILE` chooses a host CMake executable; `--skip-host` omits host
execution. On macOS the default includes the native tests below.

To validate the CMake target within a parent source build directly, add
runtime-build and business-build as shown above and configure
`-DVALDI_CLIENTSQL_LINK_CHECK=ON`. The wrapper itself never imports an archive,
adds a second runtime, or discovers runtime dependencies; it simply links the
parent's existing `valdi_runtime_ohos` target.

## Host native tests

`tests/host/CMakeLists.txt` compiles the unchanged pinned native test file,
implementation, generated bindings, and the exact same SQLite C source for
macOS. It builds real Valdi core/utilities, `Runtime.cpp`, `Context.cpp`, and
`DiskCacheImpl.cpp` from source, plus staged fmt/JsonCpp and the GoogleTest sources
bundled in staged BoringSSL (metadata commit
`54501746a6cfd366b6e7bab3c902e0f8d5826521`).
Unused runtime methods are stripped from the focused static test closure.
There are no runtime stubs or replaced database operations.

```sh
cmake -S harmony/business-build/tests/host \
  -B harmony/business-build/.artifacts/host -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build harmony/business-build/.artifacts/host --parallel 4
ctest --test-dir harmony/business-build/.artifacts/host --output-on-failure
```

All **34 native tests pass**: disk-root/name validation, WAL and readonly readers,
thread/queue ownership, SQL/parameter/result limits, shared handles, transaction
commit/rollback/timeout/reentrancy, schema/migration validation, and coordinator
release. These execute the typed native module and generated marshalling on the
host; they do not execute business JS or an OHOS application.

See [VALIDATION.md](VALIDATION.md) for the recorded source/artifact hashes and
remaining integration boundaries. `.artifacts/proof.json` contains the exact
compiler, configure commands, input provenance fingerprint, ELF checks,
per-ABI artifact hashes, and host test report.
